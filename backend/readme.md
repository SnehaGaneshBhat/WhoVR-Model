# Guna Metrics Backend

Turns raw gameplay events into a session's (S, R, T) Triguna profile,
using guna_metrics.py exactly as written -- untouched.

## Files

| File                | What it is                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `event_taxonomy.py` | The 8 raw event shapes (unchanged from the intern's file)                                                              |
| `guna_metrics.py`   | The M1-M10 metric functions + aggregation (unchanged from the intern's file)                                           |
| `compute.py`        | **New.** Plumbing: takes stored events, regroups/derives where needed, calls the metric functions, returns the profile |
| `models.py`         | **New.** Database tables: `GameSession`, `Event`                                                                       |
| `database.py`       | **New.** SQLite connection setup                                                                                       |
| `schemas.py`        | **New.** API request/response shapes                                                                                   |
| `main.py`           | **New.** The FastAPI app: 3 endpoints                                                                                  |

## Running it

```bash
pip install -r requirements.txt
uvicorn main:app --reload
```

This starts the server at `http://localhost:8000` and creates `guna.db`
(a SQLite file) in this folder the first time it runs. No separate
database server needed.

Interactive API docs (auto-generated by FastAPI) are available at
`http://localhost:8000/docs` once it's running -- useful for testing
requests by hand before the frontend is wired up.

## API

### `POST /sessions/start`

Body: `{"scenario": "wallet"}` (optional, just informational)
Returns: `{"session_id": "...", "started_at": "..."}`

Call this once, when a play session begins.

### `POST /sessions/{session_id}/events`

Body:

```json
{
  "events": [
    {
      "event_type": "decision",
      "payload": {
        "decision_id": "d1",
        "decision_latency": 4.0,
        "latency_threshold": 3.0,
        "option_switch_count": 0,
        "num_options_available": 2,
        "time_stamp": 10.0
      }
    }
  ]
}
```

Returns: `{"received": 1}`

Call this whenever the game has one or more raw events ready to send --
can be after every single event, or batched (e.g. every few seconds).
`event_type` must be one of: `task_active_window`, `repeated_attempt`,
`decision`, `information_exposure`, `trigger`, `goal_selection`,
`resource_state_change`, `duty`, `action`. `payload` must match the
corresponding shape in `event_taxonomy.py` (an extra `action` type is
also supported -- see the note in `compute.py`, it's just
`{"time_stamp": float}`, needed for M6).

### `POST /sessions/{session_id}/complete`

No body needed. Marks the session ended, computes the profile from
everything logged, stores it, and returns it.

Returns:

```json
{
  "session_id": "...",
  "profile": { "s": 0.64, "r": 0.36, "t": 0.0 },
  "breakdown": {
    "M1": null,
    "M3": { "s": 1.0, "r": 0.0, "t": 0.0, "n": 2 },
    "...": "..."
  },
  "insufficient_data": false
}
```

If every metric came back null (not enough events of any kind),
`profile` is `null` and `insufficient_data` is `true`.

## Important assumptions to know about

1. **All `time_stamp` values are seconds elapsed since session start**,
   not wall-clock time. This keeps every metric's math on one shared
   clock. The frontend should compute this itself (e.g.
   `(Date.now() - sessionStartTime) / 1000`) before sending events.

2. **The `action` event type is not one of the 8 named types** in the
   Triguna spec PDF -- it was added because M6 (Post-Trigger Behavioral
   Consistency) needs a whole-session stream of every discrete player
   action to compute a baseline actions-per-minute rate. The frontend
   should log one of these on _every_ discrete interaction, not just
   ones that also happen to be a named event (decision, goal selection,
   etc).

3. **CORS is currently open to `http://localhost:3000`** (the default
   React dev server address) in `main.py`. Update this before deploying
   anywhere real users can reach.
